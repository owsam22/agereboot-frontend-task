## Part 1 - Existing Screen

### 1. Loading state
Added a loding state while member data is being fetched.

### 2. Empty state
Handled members without a report. 

for `m_003` , the application now displays an normal empty state instead of attempting tp access report fields.

### 3. Error state
Handled API failures.

For `m_004`, the application displays an error message and provides a retry action.

### 4. Stale data
The previous member's data is cleared when switching members.

The request also uses effect cleanup to prevent an older request from updating the
screen after a newer member has been selected.


### 5. Clinician verification
Reports that have not been verified by a clinician are not presented as confirmed
clinical results.

For `m_002`, the score and biomarker values are hidden and the member sees:

"Report awaiting clinician review"

"This report has not yet been verified by a clinician. Results are not available
for interpretation until verification is complete."

Coverage is still displayed to communicate report completeness.

### 6. Verified reports
For verified reports such as `m_001`, the score and biomarker results are shown,
along with the clinician verification date.

## Part 2

### 1. Design approach

For Part 2, I redesigned the screen around how a member would actually use it instead of just changing the styling from Part 1.

The main flow is kept simple:

`Home → Search → Select member → View report`

I also added a back-to-home option from the report screen.

### 2. Home screen

I kept the home screen simple with the app name, a search action, a short introduction, and a CTA to find a report.

I also added a small 3-step guide so a new user can understand the flow quickly.

### 3. Search

Added search by member name or member ID.

The results show the member's initials, name, ID, and current status. The search is handled on the frontend using the provided member data, without changing the API.

### 4. Report screen

The report was reorganized so the important information is easier to find:

* Member details
* Report details
* Verification status
* Score, if verified
* Biomarkers
* Coverage and verification information

I changed the biomarker table into cards because they are easier to read on mobile.

### 5. Report states

The existing Part 1 behavior was kept:

* `m_002` shows the review-pending message and coverage, but not the score or biomarker values.
* `m_003` shows a proper no-report state.
* `m_004` shows the API error with a retry button.

### 6. Loading

Added a skeleton loader for the report instead of only showing a loading message. It roughly follows the report layout while the data is being fetched.

### 7. Responsive design

The layout was tested with the required `375px` width.

I focused on avoiding horizontal scrolling, keeping text readable, stacking cards properly, and making buttons easy to use on smaller screens.

### 8. Visual design

I kept the design light and simple with neutral colors, white cards, subtle borders, and a muted green accent.

I avoided gradients, excessive shadows, glass effects, unnecessary charts, and extra dashboard-style elements.

### 9. Scalability

I used search instead of a dropdown because it would work better if the number of members grows.

Biomarkers are also rendered from the API data, so adding more measurements does not require creating new UI elements manually.

### 10. Profile representation

Since the API does not provide profile images, I used member initials instead of adding made-up or external images.

## AI Usage

I did the planning, user flow, information hierarchy, and overall design decisions myself based on the task requirements.

I initially wrote the basic implementation and CSS. I used AI mainly to help with CSS refinement, responsive behavior, and cleaning up parts of the implementation.

I reviewed and changed the suggestions where needed instead of directly using everything generated by AI.

No UI kit, Tailwind CSS, or component library was used.
